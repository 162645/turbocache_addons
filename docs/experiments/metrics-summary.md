# TurboCache 项目指标与实验数据汇总

整理日期：2026-08-26。数据来自 2026-08-24～25 的历史报告和现存原始 JSON；本次只核对、汇总，没有重新压测。目录重构后的版本不能直接继承历史版本的性能结论。

## 1. 阅读口径

- 环境：单台 Apple Silicon Mac，Go 1.24.3，Colima/Docker；压测客户端与三个服务容器共享宿主机资源。不是三台物理机，也不是跨可用区部署。
- 吞吐量统一优先采用 JSON 的 `SuccessThroughput`，单位为成功逻辑操作数/秒（ops/s）。混合读写不宜直接称“查询 QPS”；内部转发、复制与重试 RPC 不单独算成业务请求。
- 延迟取客户端观测值，JSON 中的时长单位为纳秒，本文转换为毫秒。P99 不是最大延迟，也不是服务端处理时间。
- 单入口不必然等于单节点：如果 L2 开启，请求仍可能转发。必须同时说明入口数量和服务端能力开关。
- “本轮未观测到最终请求失败”只描述有限样本，不能推导为生产错误率为零；客户端重试可能掩盖单次 RPC 失败。
- 不同实验的读写比、值大小、预热、并发、持续时间和功能配置不同，不能拼成同一组性能承诺。
- 原始文件没有完整记录代码提交、硬件型号、Colima 配额及全部服务端开关。历史配置以对应报告为辅助证据，不应把现在的 Compose 默认值倒推为当时配置。

## 2. 分布式能力与性能成本：主要参考组

条件：100 并发，预热 10,000 个 Key，90% 读 / 10% 写，Value 256 B，每组约 10 秒。L1-only 使用单入口；L2 组使用三入口。三节点配置分别为 LRU、LFU、ARC，未在该实验中隔离比较三种策略。

| 场景 | 成功吞吐（ops/s） | P99（ms） | 样本操作数 | 原始数据 |
|---|---:|---:|---:|---|
| 纯 L1，单入口 | 38,144.64 | 6.359 | 381,507 | [L1 单入口](../../results/matrix/01-l1-only-single-ingress.json) |
| L2 路由，RF=1 | 30,218.27 | 12.884 | 302,250 | [L2 单副本](../../results/matrix/02-l2-rf1.json) |
| L2，RF=2，eventual | 33,340.89 | 11.681 | 333,505 | [异步复制](../../results/matrix/03-l2-rf2-eventual.json) |
| L2，RF=2，strong 配置 | 26,292.55 | 15.757 | 263,103 | [同步副本确认](../../results/matrix/04-l2-rf2-strong.json) |

这四个样本未记录最终请求失败，但只有短时间观测，不作可靠性保证。这里的 `strong` 是项目配置名，表示等待副本确认，不能据此宣称线性一致性、共识复制或事务保证。

从这组样本可计算：

- L2 RF=1 相对纯 L1 的成功吞吐降低约 **20.78%**。
- RF=2 eventual 相对 RF=1 高约 **10.33%**。副本增加可能提高入口本地命中机会，但没有隔离变量或多轮统计，不能断言“复制必然提速”。
- RF=2 同步确认相对 eventual 降低约 **21.14%**，相对纯 L1 降低约 **31.07%**。

可讲的工程结论：纯 L1 的短路径性能高于包含路由和同步复制的路径；项目通过阶梯实验量化功能成本，而不是把所有场景都包装成最高 QPS。此组不作为“全部保护模块开启”的统一基线。

## 3. Bloom 防穿透：收益与代价

条件：三入口、100 并发、约 5 秒；对照时关闭 Negative Cache，避免把负缓存的作用归给 Bloom。正常流量为 90% 读 / 10% 写、10,000 个 Key、Value 256 B。

| 场景 | 成功吞吐（ops/s） | P99（ms） | 样本操作数 | 最终失败数 | 原始数据 |
|---|---:|---:|---:|---:|---|
| 无效 Key，Bloom 关闭 | 36,921.70 | 9.368 | 184,708 | 0 | [off-missing](../../results/bloom/bloom-off-missing.json) |
| 无效 Key，Bloom 开启 | 50,913.26 | 6.320 | 254,701 | 0 | [on-missing](../../results/bloom/bloom-on-missing.json) |
| 正常流量，Bloom 关闭 | 43,262.44 | 9.050 | 216,477 | 12 | [off-normal](../../results/bloom/bloom-off-normal.json) |
| 正常流量，Bloom 开启，优化前 | 35,884.75 | 14.035 | 179,560 | 0 | [on-normal](../../results/bloom/bloom-on-normal.json) |
| 正常流量，Bloom 开启，优化后 | 37,168.50 | 10.467 | 185,938 | 0 | [on-normal-optimized](../../results/bloom/bloom-on-normal-optimized.json) |

关键数字：

- 无效 Key 对照样本：开启 Bloom 后处理吞吐提高约 **37.90%**，P99 降低约 **32.54%**。
- 正常流量样本：优化后的 Bloom 开启吞吐仍比关闭低约 **14.09%**，不能宣传为无成本提速。
- Bloom 关闭的正常流量样本有 **12 / 216,477** 次失败，约 **0.00554%**。现有 JSON 没有错误分类，原因待核实，不能擅自归因给 Bloom 或网络。
- “优化后”来自单独保存的样本，不是多轮 A/B 的统计结论；现有开关脚本也不会自动生成这个历史文件名。

特别注意：`MissingOnly=true` 会强制只读不存在的 Key。虽然 JSON 保留了默认 `ReadRatio=0.8`，实际不是 80/20 混合负载。压测器把预期的 `ErrKeyNotFound` 计为成功，因此这里的 5.09 万 ops/s 是**无效 Key 请求处理能力**，不是有效数据命中吞吐，也不是数据库回源减少量。

### Bootstrap / Fail-Open

[Fail-Open 原始样本](../../results/bloom/bloom-fail-open.json)记录：100 并发、约 3 秒、108,463 次无效 Key 请求、36,126.52 ops/s、P99 10.004 ms。

[设计报告](../design/cluster-bloom.md)另记载：人为设置 30 秒启动同步延迟，三节点未 ready 时走正常读路径，不提前 Bloom 拒绝。30 秒是人为配置的同步延迟，不是该压测持续时间，也不是实测故障恢复时间。上述客户端 JSON 本身不能证明服务端全部请求均经过 Fail-Open；严格复现还应保存同期 ready/stale/reject/fail-open 指标。

该实验支持“未就绪时采用保守旁路”的设计说明，不支持“所有并发重建和故障场景都不会产生假阴性”的绝对结论。

## 4. 节点故障与可用性观测

优先引用 [RF=2 故障样本](../../results/matrix/cluster-failover.json)：

| 项目 | 数据 / 条件 |
|---|---|
| 故障方式 | 三节点中停止 node-2，测量结束后再恢复 |
| 负载 | 100 并发，纯读，Value 128 B，预热 1,000 Key |
| 时间 | 约 20 秒；开始测量约 2 秒后停止节点 |
| 总请求 | 718,029 次 |
| 成功吞吐 | 35,896.87 ops/s |
| P50 / P95 / P99 | 2.415 / 5.385 / 8.287 ms |
| 最大延迟 | 107.395 ms |
| 最终请求结果 | 本轮样本未记录最终失败；包含客户端重试与故障转移效果 |

推荐描述：**完成单节点停机故障注入，20 秒窗口处理约 71.8 万次读取，P99 约 8.29 ms；验证客户端重试与流量切换，并观测到约 107 ms 的最大延迟。**

不要写成“故障无感”“生产高可用”“错误率恒为零”或“恢复时间小于 107 ms”。最大请求延迟不是故障发现或恢复耗时。

边界：该实验不覆盖节点重启后的数据补齐。[早期报告](benchmark-results-macos.md)记载，另一次停机后重启实验出现约 8.65% 错误率；当前结果目录没有对应独立原始 JSON，仅作报告级问题记录，不能当作本次重新确认的结果。节点健康不等于缓存已预热，不能把停机流量切换等同于完整数据恢复。

## 5. 算法与模块指标

下列数字来自[早期实验报告](benchmark-results-macos.md)，本次结合测试源码核对了实验口径，未重新运行算法实验，也未找到独立归档的原始测试日志。其证据强度低于上面有 JSON 的端到端数据。

| 指标 | 历史结果 | 条件与边界 |
|---|---|---|
| L1 命中率 | 96.98% | 12,000 Key、容量 10,500、10 万次读取；2,000 热 Key 接收约 80% 请求；先写冷 Key、后写热 Key；固定随机种子 |
| 带权哈希分布 | 最大偏差约 0.27 个百分点 | 权重 100/200/50、10 万 Key；比较实际路由份额和理论权重份额，不是实际节点 CPU 或请求负载偏差 |
| 节点移除后的映射变化 | 14.30%，理论约 14.29% | 移除权重 50 的节点；50/(100+200+50)=1/7；测量 Key 归属变化，不是数据搬迁成功率 |
| SingleFlight 合并 | 100 个并发调用合并为 1 次 loader 执行 | 同一进程、同一 Key、约 100 ms 模拟慢 loader；减少约 99% 重复执行，不是集群全局去重保证 |

对应代码：[命中率与 SingleFlight 实验](../../test/benchmark/Benchmark_test.go)、[带权哈希实验](../../test/benchmark/Benchmark2_test.go)。

命中率实验是特定预热顺序下的合成访问结果，不是线上业务命中率，也不是 LRU/LFU/ARC 三种策略分别达到该结果的证据。SingleFlight 的数字来自独立模块实验，不能描述为“三节点真实数据库回源从 100 降至 1”。

## 7. 应保留但不作为性能成绩的数据

- [最初 L1-only 三入口样本](../../results/matrix/01-l1-only.json)：136,944 / 432,693 次失败，约 31.65%。
- [后续 L1-only 三入口诊断](../../results/matrix/01b-l1-only-three-ingress-diagnostic.json)：125,293 / 354,059 次失败，约 35.39%。

关闭 L2 后，不同入口的本地缓存无法保证同一 Key 可读。这些样本说明了分布式路由的必要性，不能拿总请求吞吐充当有效缓存服务性能。

## 8. 简历建议：选 3～4 个重点

下面是有边界的可用措辞，不建议把所有数字都放进一段：

1. **分布式链路与性能**：基于 Go/gRPC 构建 L1/L2 分布式缓存，在单台 Mac 三容器环境完成路由与复制阶梯压测；100 并发、90/10 读写、256 B 负载下，双副本同步确认配置成功吞吐约 2.63 万 ops/s，P99 约 15.76 ms。
2. **防穿透权衡**：接入 Cluster Bloom 并设计未就绪旁路机制；在关闭负缓存的无效 Key 对照实验中，处理吞吐由约 3.69 万提升至 5.09 万 ops/s，P99 由约 9.37 ms 降至 6.32 ms，同时量化正常流量下的额外开销。
3. **故障验证**：完成三节点中单节点停机实验，20 秒处理约 71.8 万次读取，P99 约 8.29 ms，验证客户端重试与流量切换，并识别节点重启后预热与数据补齐边界。
4. **算法验证（补齐原始日志后优先使用）**：在 10 万 Key 的带权一致性哈希实验中，最大分布偏差约 0.27 个百分点；移除占总权重 1/7 的节点后，约 14.30% 的 Key 映射发生变化，接近理论值。

可补充但不宜独立夸大：“支持 LRU/LFU/ARC 淘汰策略”“同进程百并发热点请求合并为一次 loader 执行”。前者是功能，后者是模块实验，不应包装成全部集群路径上的统一量化成果。

避免：“企业级生产验证”“全功能稳定 6.6 万 QPS”“所有场景 P99 < 10 ms”“零错误”“自动无损迁移”“线性强一致”。

## 9. 复现与下一次数据归档

从项目根目录执行：

```bash
make build
make up
make benchmark-matrix
make bloom-experiment
RESULT_DIR=results/matrix bash scripts/experiments/resume_metrics.sh failover
```

注意：这些实验会重建项目容器或停止节点，现有脚本可能覆盖同名 JSON。先归档旧结果；不要在需要保留内存缓存数据时直接运行。当前代码、默认开关和历史状态可能不同，重跑结果应作为新批次比较。

算法实验可单独运行，不需要为了统计这些模块指标停止容器：

```bash
GOTOOLCHAIN=go1.24.3 GOWORK=off go test ./test/benchmark \
  -run 'TestCacheHitRate|TestProtectionMechanisms/SingleFlight|TestDistributedFeatures/ConsistentHashing' \
  -count=1 -v
```

下一轮应一并归档：代码版本、Mac 型号/内存、Colima CPU/内存配额、完整配置、预热条件、并发/读写比/Key 数/Value 大小、原始 JSON、错误分类、服务端监控及故障时间线。性能至少多轮报告中位数和波动；故障实验另行统计首次错误、重试次数、摘除时间、重启就绪时间和数据补齐情况。

目前尚无充分证据给出长期稳定性、最大容量、实测 Bloom 假阳性率、故障恢复耗时或多物理机扩展效率的正式成绩，不填估计数字。
